# Iris Feishu Raw Event Queue Design

Date: 2026-07-02
Status: Phase 2T proposed design
Product name: Iris

## 1. Purpose

Iris lives in Feishu group chats, so Feishu callback reliability is part of the product foundation. The architecture whitepaper requires the gateway to acknowledge Feishu quickly, enqueue raw events, and move filtering, memory extraction, and agent decisions into asynchronous processing.

Phase 2T upgrades the Feishu event ingestion boundary from an in-memory queue shape to a Redis-backed raw event queue and worker foundation.

The selected direction is option A: Feishu Raw Event Redis Queue.

## 2. Design Goals

Phase 2T must provide:

- a provider-neutral raw event queue boundary;
- in-memory and Redis implementations;
- idempotent raw event enqueue by event idempotency key;
- per-event retry attempts;
- dead-letter queue behavior after max attempts;
- a raw event worker and polling loop foundation;
- runtime status for pending count, DLQ count, and latest batch;
- an internal status API;
- no dependency on a live Redis server for unit tests;
- no change to Feishu callback external behavior.

The product goal is to make Iris's Feishu entry point production-shaped before building deeper conversation memory or proactive behavior on top of it.

## 3. Non-Goals

This phase does not implement:

- conversation memory persistence;
- message fact tables;
- semantic indexing of group chat;
- signal filtering;
- proactive decisions;
- Iris replies;
- Feishu message sending;
- admin UI;
- raw event DLQ list/replay/delete APIs;
- authentication changes for internal routes.

Those should be implemented as later phases that consume the reliable raw event stream.

## 4. Raw Event Model

Raw events are provider facts, not product decisions.

```ts
export type RawEvent = {
  idempotencyKey: string;
  provider: "feishu";
  eventType: string;
  rawBody: unknown;
  receivedAt: Date;
  attempts: number;
};
```

Rules:

- `idempotencyKey` must be stable for the same Feishu callback event.
- `provider` is fixed to `"feishu"` in this phase.
- `eventType` is copied from the normalized Feishu event when available, otherwise a safe fallback such as `"unknown"`.
- `rawBody` preserves the received Feishu callback body.
- `receivedAt` is generated by the gateway/runtime at receipt time.
- `attempts` starts at `0` and is incremented only when async processing fails.

## 5. Queue Contract

Introduce `RawEventQueue`:

```ts
export interface RawEventQueue {
  enqueue(event: RawEvent): Promise<void>;
  dequeueBatch(limit: number): Promise<RawEvent[]>;
  handleFailedEvent(input: {
    event: RawEvent;
    errorMessage: string;
  }): Promise<{
    action: "requeued" | "dead_lettered";
    attempts: number;
  }>;
  getPendingCount(): Promise<number>;
  getDeadLetterCount(): Promise<number>;
}
```

Default retry policy:

```text
maxAttempts = 3
```

The queue owns retry and DLQ behavior because it owns the storage mechanism.

## 6. Redis Storage

Redis keys:

```text
iris:events:raw:seen
iris:events:raw:queue
iris:events:raw:dlq
```

Redis enqueue uses the same shape as reindex queue:

```text
SADD seen idempotencyKey
RPUSH queue serializedEvent
```

This must be atomic through `EVAL` so duplicate Feishu retries do not enqueue duplicate raw events.

Redis failure handling:

- below max attempts: `RPUSH queue <event with attempts + 1>`;
- at max attempts: `RPUSH dlq <dead letter payload>`;
- pending count: `LLEN queue`;
- DLQ count: `LLEN dlq`.

Dead-letter payload:

```ts
{
  event: RawEvent;
  errorMessage: string;
  failedAt: string;
}
```

Phase 2T only stores and counts raw event DLQ payloads. DLQ inspection and replay can be added later.

## 7. Gateway Integration

The Feishu Gateway should remain ack-first:

```text
receive callback
verify request if configured
handle Feishu URL challenge if present
normalize enough metadata to compute idempotency key and event type
enqueue raw event
return HTTP 200
```

The gateway must not:

- parse business intent;
- classify signal quality;
- write conversation memory;
- invoke the agent;
- fetch documents;
- perform model calls.

If enqueue throws, the existing callback path may return an error. Phase 2T does not introduce a separate fallback spool.

## 8. Worker Foundation

Introduce `RawEventWorker`:

```ts
processBatch(input: { limit: number }): Promise<RawEventWorkerResult[]>;
```

Worker result:

```ts
type RawEventWorkerResult =
  | {
      status: "processed";
      idempotencyKey: string;
      eventType: string;
    }
  | {
      status: "failed";
      idempotencyKey: string;
      eventType: string;
      errorMessage: string;
      retryAction: "requeued" | "dead_lettered";
      attempts: number;
    };
```

The worker receives a processor dependency:

```ts
process(event: RawEvent): Promise<void>;
```

In Phase 2T, the default processor can be a no-op. Later phases will replace it with raw-event-to-message-fact processing.

## 9. Worker Loop And Runtime Status

Mirror the reindex worker loop shape:

```ts
{
  running: boolean;
  intervalMs: number;
  batchLimit: number;
  pendingEventCount: number;
  deadLetterEventCount: number;
  latestBatch?: {
    status: "succeeded" | "failed";
    startedAt: Date;
    finishedAt: Date;
    processedCount: number;
    failedCount: number;
    errorMessage?: string;
  };
}
```

The loop must:

- avoid overlapping batches;
- keep polling after batch-level errors;
- expose a snapshot for internal status;
- be startable and stoppable by app lifecycle.

## 10. Internal Status API

Add:

```http
GET /internal/events/status
```

When runtime is unavailable:

```json
HTTP 200
{
  "ok": true,
  "enabled": false,
  "running": false
}
```

When runtime is available:

```json
HTTP 200
{
  "ok": true,
  "enabled": true,
  "running": true,
  "intervalMs": 1000,
  "batchLimit": 50,
  "pendingEventCount": 3,
  "deadLetterEventCount": 1,
  "latestBatch": {
    "status": "succeeded",
    "startedAt": "2026-07-02T01:00:00.000Z",
    "finishedAt": "2026-07-02T01:00:01.000Z",
    "processedCount": 2,
    "failedCount": 0
  }
}
```

If status lookup fails:

```json
HTTP 500
{
  "ok": false,
  "error": "event_worker_status_failed"
}
```

## 11. Configuration

Add runtime config:

```text
IRIS_EVENT_WORKER_ENABLED=true|false
IRIS_EVENT_WORKER_INTERVAL_MS=1000
IRIS_EVENT_WORKER_BATCH_LIMIT=50
```

If disabled, the app can still accept Feishu callbacks through the configured queue dependency, but it does not start the background raw event worker runtime.

The first default runtime should use:

- existing `REDIS_URL`;
- Redis raw event queue;
- no-op processor.

## 12. Testing Strategy

Queue tests:

- in-memory queue deduplicates by idempotency key;
- in-memory dequeue is FIFO and bounded;
- in-memory failed events requeue below max attempts;
- in-memory failed events enter DLQ at max attempts;
- Redis enqueue uses atomic `EVAL`;
- Redis parser round-trips dates and defaults missing attempts to 0;
- Redis failed events requeue or DLQ correctly;
- Redis pending and DLQ counts call `LLEN`.

Gateway tests:

- Feishu callback enqueues raw event with provider, event type, raw body, received time, and attempts 0;
- duplicate callback idempotency is delegated to the queue;
- URL challenge behavior still works;
- invalid requests still fail as before.

Worker tests:

- successful events produce processed results;
- processor errors call `handleFailedEvent`;
- one failed event does not stop later events in the same batch.

Loop/runtime tests:

- loop polls worker and records latest batch;
- runtime composes Redis queue and no-op processor;
- status includes pending and DLQ counts.

Route tests:

- unavailable runtime returns disabled status;
- available runtime returns status;
- status errors return `500 event_worker_status_failed`.

Final verification:

- `npm run typecheck`;
- `npm test`;
- `python -m pytest` from `workers/ai`;
- `docker compose config`.

## 13. Product Impact

After Phase 2T:

- Feishu callback ingestion has a Redis-backed raw event queue foundation;
- duplicate Feishu retries are deduplicated before async processing;
- raw event processing can retry and dead-letter failures;
- operators can see raw event worker backlog and latest batch status;
- Phase 2U can safely build conversation message facts on top of a reliable event stream.

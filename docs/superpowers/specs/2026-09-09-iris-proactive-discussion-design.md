## 1. 用户确认与实现基线

Iris 应像协作同事一样，在工作讨论出现明显错误、推理漏洞、关键遗漏或重要风险时主动提出自己的看法，说明理由和建议。它不需要等待被 @，也不要求知识库里已有同一结论。有合理依据但尚不能证实的风险也可以提出，必须明确区分事实、推断与建议。

用户否定了“每天两条、同事项间隔 24 小时、到期催办”的上一提案，并确认本方案。以上固定频次与冷却不是本设计的默认值、回退方案或隐含验收要求。待办创建属于独立的飞书任务能力，提醒由飞书承担，不以 Iris 重复催办替代主动判断。

[当前交接](../../development/current-handoff.md)记录的最近应用版本是 `f6a6dd41`；本次文档工作没有重新探测生产，不把该记录冒充新的在线检查。

## 2. 方案选择与首轮范围

选择“消息事件驱动的独立评估，再生成并受控发送”。这比直接自由接话多一个可审计的介入判断，但能明确区分不值得说、已经解决、重复、证据失效与应该发言。

另外两条路径不采用：

- 每条消息直接自由生成回复：组件较少，但是否值得介入、重复纠缠和授权理由难以独立检验。
- 扩展旧定时提醒器：复用表面较多，但其触发条件、模板与人工审核语义不匹配本次目标。

首轮只在原试点群工作，精确目标为 `oc_637a9aca45f01943477f4e17f1fc5b9a`，对应[已核对群集合](2026-09-09-iris-shared-working-chat-design.md)的原试点群。群名只是展示，不用相似群名、机器人入群或现有三群 Q&A scope 自动扩展主动范围。

第一版读取该群的人类讨论及对该群已授权的相关文档；不读取其他群原始消息、记忆、线程、行动项或其派生回答来主动广播。现有跨群问答不变。正式建任务、Wiki 写入、外部工具执行、主动跨群通知和全公司展开均不在本轮。

## 3. 什么时候说、怎么说

### 3.1 内容判断

评估当前讨论是否存在值得现在指出的实质问题，而不是检查命中某个词或是否过了一段时间。典型情况包括：

- 本群已知事实或数字彼此冲突，讨论却继续依赖冲突前提。
- 结论超出已有依据，例如把少量访谈反馈当作已证明的整体市场需求。
- 方案忽略关键条件、依赖、成本或验证步骤，可能影响当前决策。
- 合理的专业推断揭示潜在风险，虽然尚缺足够信息证实。

一般专业知识可以帮助推理；公司具体事实必须有授权来源。模型不能为了提出意见编造测试结果、预算、公司制度或他人决定。缺少信息本身不自动触发“资料不足”群消息；只有说明它如何影响当前工作，才构成有价值的介入。

正常头脑风暴、已经注明的不确定假设、普通闲聊、无关观点差异不应被当作错误。人已经指出同样问题且在处理时，Iris 没有新的重要补充就保持沉默。

### 3.2 表达

使用自然中文，短而具体地说明“我注意到什么、为什么值得注意、建议怎样核实或调整”。事实明确时直接指出；仅属合理怀疑时用“我担心”“如果这个前提成立”等措辞。不能把内部评分、英文策略词或模型信心数字当作群聊内容。

示例仅是表达样例，不是生产消息：

> 我担心这里把“受访者喜欢”直接当成了“会付费”。这批访谈能说明吸引点，但还不能证明付费意愿。建议把是否愿意付费、愿意付多少单独验证，再决定是否扩大投入。

不强制每次套三段模板，不人身评价，不要求成员先批准才能看到这一条低风险意见。用户追问原因或让 Iris 改写时，继续正常问答并保留底层来源。

### 3.3 不设固定发言间隔

新问题或实质新依据可以触发下一次发言，不因上一条刚说过而被固定冷却或每日配额拒绝。防打扰依赖问题身份、证据变化、是否已回应/已解决和用户反馈，而非时钟。

短句合并只用于理解连续输入；工作队列不能通过不断延长合并等待饿死评估。平台限流、网络重试与异常风暴保护属于技术故障处理，需要状态可见，不能伪装成日常产品限额或丢弃正常的新问题。

## 4. 模块与数据流

采用新的 `proactive-discussion` 领域，保留旧 `proactive-signals` 的人工提醒合同，不整体重写聊天或记忆系统。

1. **登记器**：普通人类消息成功落事实库后，幂等登记同群评估任务。登记失败交给 raw-event 重试，重复处理不能重复登记；模型不在事件回调、消息删除保护锁或事实事务内执行。
2. **上下文构建器**：独立后台 worker 领取任务后，读取当前同群窗口、相关同群来源及已有问题状态。采用现有有界正文预算与来源验证，不启用全局 memory extraction，也不直接使用自动装配跨群源的 Q&A runtime。
3. **语义评估器**：输出是否值得介入、问题身份、依据、推断、建议与跳过理由；默认可以不发言。它只产出结构化判断，不操作飞书。
4. **策略与生成器**：Core 校验模型结果和当前策略，将可介入判断生成自然语言草稿，并记录自动策略授权。生成的草稿不能新增评估中没有的事实前提。
5. **投递器**：发送前复验最新上下文、来源、问题版本和开关，通过才发出一条群内意见；保存真实回执。错误、取消和不确定发送结果只进内部状态，不发“资料不足”或技术报错打断讨论。

@ 消息继续由原有回答链路负责，不为同一 @ 请求再生成一条主动回答。它们仍可作为随后评估的同群上下文。排除 Iris 自身及其他机器人输出作为主动触发源，避免互相接话循环。

新增 worker 与普通回答失败隔离；一个评估失败不能关闭普通问答，也不能通过反复重放 raw event 重复发送已完成的回答。第一版使用既有 Postgres 持久化/租约模式承载评估与投递，不新增服务或另建模型基础设施。

## 5. 评估合同、问题状态与来源

### 5.1 结构化合同

输入包含精确群、触发消息身份/正文 hash、上下文版本、允许的来源引用、已知问题及其最近状态。输出至少包含：

- `decision`：`intervene` 或 `skip`。
- `reason`：发现实质问题、已有同等意见、已解决、重复、无工作价值、缺乏可说明的依据等可审计类别。
- `issueRef`：输入中的现有问题 ID 或明确的新问题描述；不能返回另一个群的任意 ID。
- `evidenceRefs`：仅引用输入中存在的授权来源；公司事实前提与一般推理分开保存。
- `observation`、`reasoning`、`suggestion`：要指出的问题、解释和建议；推断显式标记不确定性。
- `materialChange`：相对同一问题上次发言新增了什么；换一种措辞或新到了一条无关消息不算新依据。

Core 验证来源属于允许集合、字段与文本有界、问题身份合法，以及生成内容未扩大事实范围。结构合法不等于判断一定正确；语义误报和有价值介入由验收语料与真实试点检验。

### 5.2 持久化与去重

领域事实保存评估任务/租约、评估结果、同群问题及证据版本、策略授权、待投递内容和投递回执。来源沿用已有事实身份，不额外复制全量群历史。

任务键绑定群、消息身份、正文版本与策略版本。问题由 Core 分配身份，语义评估只能匹配提供的同群问题或提出新问题；同群提交串行校验，避免两个并发评估把同一问题各建一份。仅靠模型新造 ID 或字符串完全相等不能充当语义去重。

投递键绑定同群问题、实质依据版本和策略版本；唯一约束与事务处理重复登记、模型重试和进程重启。问题可处于观察、已发言、已解决或用户要求不再跟进的状态。追加的评估/授权/投递事件保留可追溯性，不覆盖原先为什么说、为什么取消。

同一问题无实质新依据不重复。新消息纠正了前提或表明问题已解决时，旧草稿失效；新问题不受旧问题状态影响。纯粹重启 worker、重复回调、策略版本变化或时间流逝不能把旧提醒复活。

### 5.3 来源与连续对话

`proseSources` 保存所有存续问题文字的完整暴露来源，含未引用资料和已暴露的问题目录文字来源。
新问题绑定全部输入来源，更新时保留原描述的来源与新输入来源；每次复用先完整复验并传入下一次
evaluation/delivery 来源。旧记录来源证明为 null 时不猜测回填，不向模型暴露其文字；身份及
暂停/未知状态继续存在，目录不完整仍阻止新问题绕过。1000 条来源上限不能通过截断证明绕开。

源与目的必须满足本次主动策略的可见范围。模型输入中所有实际暴露的消息/文档都要绑定来源与版本，不只记录最后引用的两句。新鲜读取失败、删除、失权或不明 provenance 不回退旧正文。

本群 Iris 历史回答不是独立事实。若要用于语言衔接，须检查其底层来源；带其他群来源或来源不明的旧回答不能洗成纯本群证据。主动发言的真实回执需要保存同样可复验的来源链，使随后 @Iris 的追问和改写能够复用内容但不能绕过撤销或删除规则。

文档只使用目的群已有阅读授权下的证据；本轮不创建新文档授权。模型不得根据群聊或文档中的指令改变策略、开启工具或申请扩大可见范围。

## 6. 授权、发送前检查与暂停

新策略默认关闭、群名单默认空，单群策略记录精确群 ID、版本、启用状态及真实操作者。`proactiveSpeech` 仍是紧急总闸；新 runtime 同时检查自身开关、精确名单、当前群可读和可主动发言状态。旧 planner/delivery 不因新能力启用而一起开启。

允许发送的依据是已批准的单群低风险参与策略，记录为 `authorizationKind=policy`，不是 `human_approved`。不调用旧人工批准 API 冒充真人点击；旧提醒候选仍受原来人工审核约束。新策略也不批准知识写入、正式任务或其他外部行动。

生成后、实际外发前必须检查：

- 当前策略版本、持久化 runtime、群状态与机器人访问仍允许。
- 触发和暴露来源未删除、正文/版本一致、文档仍可读。
- 有关问题未被人纠正或解决，没有已发送的同等意见，也没有有效的用户停止跟进状态。
- 最新群消息序列已检查；若生成期间讨论变化，重新评估而不是盲发旧稿。最终提交以检查过的上下文版本做 CAS；新事件先提交时，旧稿不能抢过它外发。

本地授权、问题状态、已知删除与发送声明共用明确事务/锁顺序；模型和远端请求均不持有长事务。外部消息读取和发送不是分布式原子事务，不能宣称防住最后一次成功远端检查后尚不可观测的修改。

外发使用稳定标识与真实回执；已开始发送或结果未知时不因超时盲重发，不谎称已撤回。结果未知阻止同一问题的新版本投递，先对账或由操作者处理；独立的新问题不因此受到人为时间冷却。

成员直接回复某条主动意见，明确要求“不再跟进这件事”时，绑定真实成员与该问题暂停，不能让另一个人的被引用文本伪造反馈。模糊反馈不擅自关闭整群；管理员可通过既有受保护的控制面暂停全群主动能力。用户停止跟进不能因时间到了自动解除；由后续明确恢复指令或受权操作者恢复。可复用原有真实回调验证机制，但不照搬旧提醒的固定 30 天抑制。

## 7. 测试与有限验收

以下是待实现的验收门禁，不是本次已通过的结果：

| 场景 | 必须观察到的结果 |
|---|---|
| 无 @ 的明确事实矛盾、推理漏洞或关键遗漏 | 能识别问题，给出理由和有用建议，不要求先存 Wiki |
| 有根据但未证实的风险 | 可主动表达怀疑；不升级成已验证事实，不泄露英文策略词 |
| 连续出现两个不同的重要问题 | 两个均可被处理，第二个不因刚发过而受固定间隔或日配额阻断 |
| 同一问题换句话说、重复回调、重启或模型重试 | 没有新依据就没有第二次投递，不出现机器人自触发循环 |
| 正常闲聊、合理假设、已有人处理且无新增意见 | 保持沉默，不强行挑错或发资料不足模板 |
| 生成后人纠正、来源修改/删除、权限撤销、暂停 | 旧稿不发送；已知取消与发送竞态由真实 Postgres 测试证明 |
| 本群旧 Iris 回答底层来源来自别群 | 不通过本群回话把外群原文带进主动评估/发言 |
| 发送成功但记回执失败或网络结果未知 | 不盲重发；状态和恢复入口可见，不伪造成功 |
| @ 问答、闲聊、三群共享问题、受治理任务/知识流程 | 原能力和授权边界不变，同一 @ 不双答 |
| 用户要求不再跟进某问题 | 同问题暂停，其他新问题仍可介入；恢复需要明确指令 |

实施计划须将上表落实为确定性测试、真实 Postgres 竞态与模型场景集。模型检查覆盖全部行为类别，逐例核对该说/不该说及理由，至少重复两轮；不能把 JSON 合法或关键词命中当作判断质量通过。

本地测试、精确 SHA CI、内部真实模型草稿和真实飞书群可见投递分阶段记录。先在关闭外发的环境用脱敏/合成场景检查，再在获准单群执行一次有界真实投递及停止跟进验证，不伪造 @、审批或回调。

无 P0/P1 缺口且上述门禁通过后进入单群日常试用，不扩成无限红队或全量历史扫描。复杂主题归并、更多附件、多群主动参与和更丰富意见样式作为后续事项；当前验收暴露的核心误报、漏掉明确风险、重复发送或权限失败仍是阻塞。

## 8. 发布与失败处理

文档确认不是部署批准的替代证据。实施后按当时的精确提交、镜像、备份、健康、队列和群目录核对制定发布步骤，不复用共享群聊发布脚本的旧环境假设。

新增 runtime 独立启停，关闭主动能力时保留原来基础问答和已批准三群共享。新评估/投递的错误、待处理、死信、结果未知和最后成功时间要进入状态页，不把启用但不工作的组件标为健康。

出现授权失败、不可控重复、严重误报或核心故障时，关闭新主动投递并保留诊断事实，不清空历史表或扩大权限补救。技术异常向操作者报告，不主动向群连续发送失败消息。已有正式任务创建与提醒机制保持独立。

## 9. 与旧设计的关系

[2026-08-04 候选上下文设计](2026-08-04-iris-proactive-candidate-context-design.md)与既有反馈设计继续约束旧时间触发、人工审核提醒，不改写其历史验收。它们的“无自动投递”不能被误当作本次新策略仍需逐条人工审核，也不能反过来让新策略批准旧候选。

[共享工作群聊设计](2026-09-09-iris-shared-working-chat-design.md)仍约束跨群提问及来源链。本设计不改变其范围，不把已批准的被动 Q&A 自动变成主动广播。

# Iris Internal Status Generated Timestamp Design

## Problem

The internal status snapshot is intended to be the operator's quick view of Iris health. Without a generation timestamp, the backend or future admin UI cannot clearly show whether the status was just produced or is stale from a cached response, retry, proxy, or browser state.

For the first 20-30 internal users, a simple timestamp is enough to make status debugging more trustworthy.

## Decision

`GET /internal/status` includes a top-level `generatedAt` ISO timestamp:

```json
{
  "ok": true,
  "generatedAt": "2026-07-03T07:30:00.000Z",
  "components": {}
}
```

The timestamp represents when the consolidated snapshot response is generated by the API process.

## Implementation Notes

- `buildApp` accepts an optional `now` dependency for deterministic tests.
- Production defaults to `new Date()`.
- The timestamp is only added to the consolidated status endpoint, not every individual component status endpoint.

## Quality Bar

- Existing component status payloads remain unchanged.
- The timestamp is ISO-8601 serialized.
- Tests can assert an exact timestamp without depending on wall-clock time.
